# Shikibu を Google Colab で回すための設計方針

学習は Google Colab（L4 ランタイム）で行うことを基本とする。Colab の制約は厳しいので、Shikibu の自由区画（第S部）はこの文書の方針に合わせて作る。

## 1. Colab の制約

| 制約 | 影響 |
|---|---|
| CPU のコア数が少ない（ランタイムによる。実行時に `os.cpu_count()` で確認する） | 特徴抽出（CPU）が律速になる。**1局面あたりの CPU 時間がすべて** |
| 計算単位（CU）は時間で消費される | 速度がそのまま費用になる。速度が10倍違えば費用も10倍違う |
| データは Google Drive に置く（ローカルディスクは小さい） | Drive からローカルへのコピーを先読みで隠す |
| セッションは途中で切れる | 定期保存と再開が必須 |
| セッションごとに環境がまっさらになる | Rust のビルドを毎回やり直さない工夫が必要 |

## 2. 速度の目標と予算

- 目標：**ローダー全体で毎秒100万局面**（40億局面の1周が約1.1時間）。
- ローダーのスレッド数は「論理コア数 − 1」（1つは Python の主スレッドと GPU への転送に残す）。
- したがって、**1スレッドあたり毎秒20万〜25万局面（1局面あたり約4µs）**の純粋計算速度が必要になる。1局面の中身は「PSV の解読1回 ＋ 両視点の特徴抽出 ＋ 昇順への並べ替え」。

## 3. 実装の原則

1. **特徴抽出の内側でメモリを確保しない。** ラインの走査ごとの `Vec` の作り直し、盤面のコピー、文字列の生成をしない。スレッドごとに作業領域を1回だけ確保して使い回す。
2. **SFEN 文字列を経由しない。** PSV から盤面の配列へ直接解読する（`extract_sfen` はテスト用の入口として残す）。
3. **出力はそのまま numpy 配列にする。** スレッドがバッチ単位で連続領域に書き込み、Python には1回のコピー（またはコピーなし）で渡す。Python 側で局面ごとのループをしない。
4. **Python の主スレッドの仕事は最小限。** 受け取った配列を `torch.from_numpy` で包み、固定メモリ（pinned memory）経由で `non_blocking=True` で GPU に送るだけにする（M3 で実装）。
5. **正しさは既存のテストで守る。** 高速化の前後で `python -m pytest -q tests` が全件通ること。

## 4. Google Drive とローカルディスク

- データは 1GB（2,500万局面）のシャードで Drive に置く。
- `BatchLoader` の `cache_dir` に `/content/shk_cache` を指定し、`max_cached` は 3 とする。
- Drive からのコピー速度（MB/秒）をログに出す。毎秒100万局面には 40MB/秒が必要。

## 5. ビルドの使い回し

- 初回だけ Colab 上で Rust をインストールし、`maturin build --release` で wheel を作って Drive に保存する。
- 2回目以降は Drive の wheel を `pip install` するだけにする（ソースが変わったときだけ作り直す）。

## 6. 速度の確認

Colab 上で次を実行し、結果を記録する。

```
python perf/perf_check.py --profile colab
```

## 7. それでも速度が足りないときの退路（優先順）

1. CPU の多いランタイム（ハイメモリなど）を選ぶ。
2. 1回の学習に使う局面数を減らす（例：40億 → 20億）。
3. 手元の PC（多コア CPU ＋ ROCm 環境）で学習する。Shikibu は PyTorch と Rust だけで動くので、Colab 専用の作りにはしない。
