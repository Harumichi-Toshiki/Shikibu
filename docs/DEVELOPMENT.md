# 開発の進め方

Shikibu を開発・変更する人（人間、または Claude Code）のための文書です。
変更禁止ファイルの扱い、テストの実行、マイルストーンの経緯、未解決の課題をまとめます。

## 1. 変更禁止ファイルと `check_protected.py`

### 1.1 変更禁止のファイル

次のファイルは、`PROTECTED.sha256` に SHA-256 が書かれていて、変えてはいけません。

| ファイル | 役割 |
|---|---|
| `docs/DESIGN.md` | 設計書（凍結区画の第F部を含む） |
| `docs/COLAB.md` | Colab の方針 |
| `tests/conftest.py`・`tests/test_m1_acceptance.py`・`tests/test_m2_acceptance.py`・`tests/test_m3_acceptance.py`・`tests/test_m4_acceptance.py`・`tests/test_m51_acceptance.py`・`tests/test_m6_acceptance.py` | 受け入れテスト（M6 の参照実装は `tests/halfkp_ref.py`・`tests/halfkp_nnbin.py`） |
| `tests/m2_data.py`・`tests/m3_data.py`・`tests/m4_ref.py`・`tests/golden/raypair_golden.json` | テスト用のデータと参照 |
| `reference/raypair_ref.py` | 特徴量の参照実装（付録A） |
| `perf/perf_check.py` | 速度の合格判定 |
| `check_protected.py` | この確認スクリプト自身 |

- `PROTECTED.sha256` 自体は、この表には入っていません（自分の内容は、自分では検査できないため）。ただし、同じく変更禁止として扱ってください。
- 変えてよいのは、`crates/`、`python/`、`tools/`、`bench/`、`configs/`、`notebooks/`、そして `docs/` の文書（`DESIGN.md` と `COLAB.md` を除く）、`REPORT_*.md`、`README.md` です。

### 1.2 凍結区画の変更

- `docs/DESIGN.md` の第F部（凍結区画）は、既存の定義を書き換えてはいけません（§0.3）。
- 変更が必要になったら、既存の ID は残したまま、新しい ID（例：`RayPair_v2`）を追加します。
- 凍結区画に疑問や矛盾を見つけたら、自分で解釈を決めずに作業を止めて報告します（§0.3）。
- 設計書の改訂は、設計の担当（持ち主）が、両リポジトリに同時に反映します。

### 1.3 確認コマンド

```
python check_protected.py
```

- 全部一致していれば、`OK` と表示して終了コード 0 で終わります。
- 変わったファイルは `CHANGED <パス>`、無いファイルは `MISSING <パス>` と表示し、`NG: n file(s)` で終了コード 1 になります。
- 各コミットの前に、この確認を通してください（この文書群の作業も、そうしています）。

## 2. キット（zip）で変更禁止ファイルを更新する手順

M2〜M4 では、変更禁止ファイルが zip（「キット」）で届き、次の手順で入れました（REPORT_M2.5・M3・M4）。

1. キットの中の `KIT.json` に書かれた SHA-256 と、キットのファイルを照らす。一致しないものは入れない。
2. 一致したファイルを、リポジトリの同じパスへコピーする。
3. `PROTECTED.sha256` にキットの行が入っていれば、それも取り込む（M2 のテストの行は、M2.5 で取り込んだ）。
4. `python check_protected.py` が `OK` になることを確かめる。
5. コミットする（キットの導入は、1つのコミットにまとめる。例：`Install kit M4`）。
6. リポジトリ直下に置いた zip は削除する。

注意：
- 変更禁止のパスへの書き込みが、自動の審査で拒否されることがあります（REPORT_M2）。拒否された場合は、回避せずに持ち主に報告してください。
- 変更禁止ファイルを変えたのに `PROTECTED.sha256` を直して辻褄を合わせるのは、してはいけません。

## 3. テストの実行

### 3.1 環境

- Python 3.13 と、仮想環境を使ってください（`maturin develop` は仮想環境が無いと動きません。REPORT_M1）。
- 必要なパッケージ：`maturin`・`pytest`・`numpy`・`cshogi`・`torch`（M3・M4 のテストが使います）。

```
python -m venv .venv && . .venv/bin/activate
pip install maturin pytest numpy cshogi torch
maturin develop --release -m crates/shk_feat/Cargo.toml
```

> `.venv/` は `.gitignore` に入っています（M5.1）。それでも、仮想環境はリポジトリの外に作ることを勧めます。

### 3.2 実行

```
python -m pytest -q tests
python check_protected.py
```

- 期待する結果：`100 passed`、`OK`。
- 内訳：M1 34 件（`test_m1_acceptance.py`）、M2 15 件（`test_m2_acceptance.py`）、M3 13 件（`test_m3_acceptance.py`）、M4 11 件（`test_m4_acceptance.py`）、M5.1 15 件（`test_m51_acceptance.py`）、M6 12 件（`test_m6_acceptance.py`）。
- この文書の作成時の実行：Python 3.13、PyTorch 2.14.1（CUDA 版の wheel、CPU で実行）、`73 passed in 62.27s`。

テストの環境変数：

| 変数 | 既定 | 意味 |
|---|---|---|
| `SHIKIBU_FEAT_MODULE` | `shikibu_feat` | テストが読む Rust 拡張のモジュール名 |
| `SHIKIBU_N_RANDOM` | 20000 | ランダム局面テストの局面数（増やすと時間がかかる） |

テストが失敗したときは、`python -m pytest -q tests -x` で最初の失敗を見てください。

### 3.3 速さの確認

```
python bench/bench_loader.py --records 1000000                  # ローダーの速さ（スレッド数を変えて計測）
python perf/perf_check.py --profile dev                          # 開発環境の合格判定
python perf/perf_check.py --profile colab                        # Colab 本番の合格判定（Colab で実行）
```

- `perf_check.py` は、1スレッドの純粋計算と、ローダーの速さを両方の version で測り、基準に届かなければ `FAIL` にします（終了コード 1）。
- 基準：dev は純粋計算 20 万局面/秒（1スレッド）と、ローダー 4 スレッドで 50 万局面/秒。colab は、純粋計算 20 万局面/秒（1スレッド）と、ローダーを論理コア数 − 1 スレッドで 100 万局面/秒。

### 4.1 各マイルストーンで決まったこと（要点）

- **特徴量の正しさ**：凍結区画（§F2・§F7・付録B）の正解データと全件一致する。差分更新の検査を含む全計算は、付録Bと照らす。
- **再開**：シャッフルなしなら、止めずに回したときとビット単位で一致する（テスト）。シャッフル窓の中の局面は失う（重複はしない）。
- **周回ごとのファイル順**：`seed + 周回番号` で並べる。M3 の checkpoint からの再開は、その周回の残りを旧い順のまま続ける（M4）。
- **勝敗欠損の判定**：全学習ファイルからの連続ブロック（`scale_sample`）で行う（M4）。M3 のテストの冒頭には「先頭の 1 ファイル」と書かれているが、テストは変更禁止なので直していない。
- **量子化**：丸めは「0 から遠い方への四捨五入」（`std::lround` と同じ）。`qforward` は蓄積値が int16 の範囲を超えたら止まる（起きない見込み）。

## 6. 作業の進め方（この作業での取り決め）

- 1つの文書（または1つの作業）ごとにコミットします。各コミットの前に `python check_protected.py` を実行します。

- 報告書は、マイルストーンごとに `REPORT_M<番号>.md` としてリポジトリ直下に置きます（報告は日本語）。
- 作業用の一時ファイル（テストの出力など）は、リポジトリの外に置きます。
