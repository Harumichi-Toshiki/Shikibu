# 運用の注意とトラブル対処

Colab での学習を回すときの注意、切れたときの再開、データと速さの性質、よくあるエラーの対処をまとめます。
手順そのものは `docs/GUIDE_COLAB.md` を見てください。

「確かめた」と書いたものは、この開発環境（Linux・CPU・小さなデータ）で実際に実行して確かめたものです。
「Colab で」と書いたものは、Colab でしか確かめられないため、持ち主からの報告か、Colab の仕様にもとづいています。

---

## 1. 最も大事な心得：`mon.watch()` を止めない

- Colab は、セルが実行中でないと「操作なし」とみなして、ランタイムを切断することがあります（Colab の仕様）。
- 学習は裏のプロセスで動きますが、**表示のセル（`mon.watch()`）が動いていることが、Colab から見て「操作中」になります**。
- 裏で学習を回している間は、`mon.watch()` を止めずに動かし続けてください。
- **別のセルを実行したら、すぐに `mon.watch()` を実行し直してください。** 実際に、これをしなかったために学習が切断された経験があります（持ち主の報告）。
- 表示の■（停止）ボタンは、表示だけを止めます。学習は続きます。切断を避けたいときは、セルを動かし続けてください。

## 2. 切れたあとの再開

### 2.1 何が消えて、何が残るか

| 場所 | 切断後 |
|---|---|
| `/content`（ローカルの一時領域） | **消える**。`/content/shk_cache`（コピーした PSV）、`/content/run_config.toml`（このセッションの設定）、`/content/shk_train_stdout.txt` も消える |
| 入れた Python パッケージ（`shk_feat` の wheel を含む） | **消える**（ランタイムごとに入れ直す） |
| Google Drive（`MyDrive/...`） | **残る**：学習データ、リポジトリ、wheel、`runs/<設定名>/`（`checkpoint.pt`・`log.jsonl`・`status.json`） |

（これは Colab の仕様です。この環境では確かめていません。）

### 2.2 手順

1. ランタイムに再接続する。
2. ノートブックの「1. Google Drive をマウントする」を実行する。
3. 「3. wheel（`shikibu_feat`）をインストールする」を実行する。**パッケージは消えているので、この手順は必ず必要です**（Drive に保存した wheel から数秒で入ります）。
4. 「2. リポジトリを取得（または更新）する」を実行する。
5. 「4. 設定を選ぶ」を実行する。`/content/run_config.toml` を作り直すためです。**この節を飛ばすと、次の `mon.start` が失敗します。**
6. 「5. 学習を裏で開始する」（`mon.start`）を実行する。`checkpoint.pt` があれば、自動で `--resume` が付きます。
7. 「6. 進み具合を表示する」（`mon.watch`）を実行する。

学習は、`checkpoint.pt` の時点から続きます。`log.jsonl` には `"resumed": true` の `start` 行が追加されます（上書きされません）。

### 2.3 失われるもの

- **最後の保存より後の分は失われます。** 既定では 30 分ごとに保存するので、切断の直前の最大約 30 分の学習が失われます。
- 確かめた例：`mon.stop()` を、保存が 50 ステップのときに 90 ステップで実行すると、次の `start` は 50 ステップから再開しました（40 ステップ分が失われた）。
- `shuffle_buffer > 0` のときは、窓の中の局面も失われます（重複はしません）。

### 2.4 保存の間隔を短くしたいとき

- `save_every_minutes` を短くします（例：10）。ただし、保存には `checkpoint.pt` の書き込みがかかります。大きさは、v0 が約 23MB（オプティマイザを含む。確かめた）、v1 はモデルだけで約 59MB で、オプティマイザを含めるとその数倍です（REPORT_M3）。Drive への書き込みに時間がかかるので、短くしすぎないでください。
- 保存の間隔を 0 にしてはいけません（毎ステップ保存になります。`CONFIG.md` の注意を参照）。

## 3. 二重起動の危険（必ず読んでください）

**同じ出力フォルダで学習が2つ同時に動くことがあります。** これは、確かめた事実です。

- `mon.start` は、このプロセスで起動した学習（`_proc`）だけを覚えています。
- 次の場合、前の学習が動いたままでも、`mon.start` は新しく学習を起動します。
  - ランタイムを再起動した後や、別のカーネルで `import shk_monitor` し直した後に `mon.start` を実行したとき。
- `checkpoint.pt` が既にあれば、新しい方には `--resume` が付くので、2つが同じ `checkpoint.pt`・`log.jsonl`・`status.json` に書き込みます。
- 確かめた例：1つ目の学習が動いている最中に、別のプロセスから `start` すると、2つの学習が同時に動き、2つ目は 1つ目の保存（150 ステップ）から再開しました。

対処：

- `mon.start` の前に、学習が動いていないかを確かめてください（セルで `!pgrep -af shikibu.train` を実行する）。
- 動いていれば、表示（`mon.watch`）で様子を見てください。止めるには `!pkill -f shikibu.train` を使います（`mon.stop()` は、このプロセスで起動した学習にしか効きません）。
- 止めるときは、最後の保存より後の分が失われます（2.3）。

（Colab で、ランタイムの再起動後に前の学習が残るかどうかは、確かめていません。）

## 4. 止め方と終わり方

| 状態 | 起こること |
|---|---|
| `mon.stop()` | 学習のプロセスに終了の合図を送る（SIGTERM）。最後の保存より後の分が失われる。次の `mon.start` は、最後の保存から再開する（確かめた） |
| `max_steps` に到達 | 最後に保存して終わる。`status.json` は `done`。これはエラーではない |
| 異常終了 | `mon.watch` が「異常終了（終了コード …）」と表示し、学習プロセスの最後の出力を表示する（`/content/shk_train_stdout.txt`） |
| 設定・データのエラー | 終了コード 1。`エラー: …` と表示され、`status.json` の `phase` が `error` になる |

## 6. eval_scale の推定について

### 6.1 eval_scale とは

教師の評価値（cp）を勝率に変えるための定数です（`勝率 = sigmoid(cp / eval_scale)`）。学習の前に1度決めて、`.shk` のヘッダに記録します。
設定が `"auto"` なら、勝敗から推定します（§S4）。

### 6.2 引き分けが多いと、推定値は大きめに出る（確かめた）

真の値を 600 とした人工データ（勝敗は `sigmoid(score / 600)` の確率で振る。局面 2 万件）で、引き分けの割合を変えて推定しました。

| 引き分けの割合（一様に混ぜた） | 推定値（eval_scale） |
|---|---|
| 0%（引き分けなし） | 605.1 |
| 30% | 1,616.7 |
| 60% | 3,344.5 |

- 引き分けは、目標の 0.5 に近づける形で BCE に効くので、推定値は「平らな」方向（大きい方）へ寄ります。
- ただしこれは、引き分けを評価値と無関係に混ぜた人工データでの結果です。実際の教師データで引き分けがどう現れるかは、確かめていません。
- 推定値が大きいと、教師勝率が 0.5 に寄るので、学習は弱い信号になります。推定値が探索範囲の端（50 または 5,000）に張り付いたら、勝敗と評価値の対応が弱いと考えてください（`shk_tools estimate-scale` が警告を出します）。
- 確かめた例：勝敗と評価値が無関係な小さなデータでは、推定値が 4,999.8（上限に張り付く）になり、警告が出ました。

### 6.3 推定値を変えたいとき

- 学習の途中で `eval_scale` を変えても、再開では無視されます（checkpoint の値が使われる）。
- 別の値で学習し直すには、**別の出力フォルダ**で新しく始めてください。
- 手で決めるときは、設定の `eval_scale` に数値を書きます（推定はしない）。

## 8. よくあるエラーと対処

報告書（REPORT_M1〜M4）に出てきたものと、この文書の作成で出たものを集めました。

### 8.1 インストール・ビルド

| 表示 | 原因 | 対処 |
|---|---|---|
| `Couldn't find a virtualenv or conda environment` | `maturin develop` は仮想環境が無いと動かない | `python -m venv` で仮想環境を作って有効にする（REPORT_M1） |
| `ModuleNotFoundError: No module named 'cshogi'` | テストや正解データ作りに cshogi が要る | `pip install cshogi` |
| `ModuleNotFoundError: No module named 'torch'`（テストの収集時） | M3・M4 のテストは PyTorch が要る | `pip install torch`。README の旧い手順には無かった |
| `ModuleNotFoundError: No module named 'shikibu_feat'` | Rust の拡張が入っていない | `maturin develop --release -m crates/shk_feat/Cargo.toml`。Colab では「3. wheel」の節を実行し直す |
| `pip install` や `rustup` が Colab で失敗する | ネットワークや Colab の制限（未確認） | ランタイムを再接続して、「3. wheel」の節からやり直す |

### 8.2 学習の開始

| 表示 | 原因 | 対処 |
|---|---|---|
| `checkpoint.pt がある。続けるなら --resume を付ける（上書きはしない）` | 同じ出力フォルダに学習の途中がある | `--resume` を付ける。`mon.start` は自動で付ける。終了コード 1 で正しく止まる |
| `勝敗が欠損している（psv_stats）…` | `game_result == 0` が 95% 超 | データを確認する。欠損を許すなら `allow_missing_results = true`、`lam = 1.0`、`eval_scale` を数値にする（`CONFIG.md`） |
| `勝敗が欠損のときは lam = 1.0 が必要` | 欠損を許したが、`lam` が 1.0 でない | `lam = 1.0` にする |
| `勝敗が欠損のときは eval_scale を数値で指定する` | 欠損なのに `"auto"` | `eval_scale` に数値を書く |
| `学習データが1つも無い（data.train_paths / data.train_glob）` | `train_glob` に当たるファイルが無い | Drive のパス（フォルダ名や日本語）を確かめる。「4. 設定を選ぶ」の表示（学習用の PSV の数）で確かめられる |
| `未知のセクション: …` / `[…] に未知のキー: …` | 設定のキーのつづりの間違い | `CONFIG.md` のキーと照らす |
| `eval_scale は "auto" か正の数` | 文字列や負の数 | `"auto"` か正の数にする |
| `train.total_steps と train.max_steps は1以上` | 書き忘れ | 両方を書く |
| `output.out_dir を指定する` | 書き忘れ | 書く |

### 8.3 再開

| 表示 | 原因 | 対処 |
|---|---|---|
| `checkpoint の network / lam が設定と違う` | 設定の `network` や `lam` を、途中で変えた | 元の値に戻す。変えたいときは別の出力フォルダで始める |
| `checkpoint の file_perm が学習データのファイル数と合わない` | `train_glob` のファイル数が変わった | 元のファイル構成に戻す。変えたいときは別の出力フォルダで始める |
| `resume_state とファイル数が違う` | 同上（ローダーの検査） | 同上 |
| `checkpoint.pt が無いので最初から学習します` | `--resume` を付けたが、`checkpoint.pt` が無い | 正常（警告）。最初から学習する |

### 8.4 データと `.shk`

| 表示 | 原因 | 対処 |
|---|---|---|
| `…: サイズが40バイトの倍数でない` | PSV が切れている、または PSV ではない | ファイルを確かめる。Drive からコピーし直す |
| `…: 末尾が40バイトの倍数でない` | 読んでいる途中で切れた | 同上 |
| `出力先に shard_XXXXX.psv が既にある。空のフォルダを指定する` | `shk_tools shuffle` の出力先が空でない | 空のフォルダを指定する（既存のシャードを消すかは持ち主が決める） |
| `ファイルの長さが本体の長さと合わない（切れている可能性）` | `.shk` が途中で切れた | 書き出しをやり直す |
| `CRC32 が一致しない` | `.shk` が壊れている | 書き出しをやり直す。Drive の同期の途中でないかを確かめる |
| `書き出しの確認に失敗（…）` | 書き出した `.shk` を読み直したとき、一致しなかった | 書き出しをやり直す。繰り返すなら checkpoint を確かめる |
| `コピー失敗: …` | `cache_dir` へのコピーが失敗した（容量か Drive の接続） | ローカルの空き容量と Drive の接続を確かめて、再開する |
| `ローダーの作業が途中で止まった` | 作業係のスレッドが止まった | ログ（`log.jsonl`）と画面の最後の出力を確かめ、再開する |

### 8.5 その他

| 表示 | 原因 | 対処 |
|---|---|---|
| `ZeroDivisionError: integer modulo by zero`（トレースバック） | `log_every_steps = 0` | 1 以上にする（検査されていない） |
| `ValueError: 出力先に …`（トレースバックつき） | `shk_tools shuffle` の出力先が空でない（このコマンドだけ、エラーを整えて表示しない） | 空のフォルダを指定する |
| `status.json` の `phase` が `error` | 設定・データのエラーで止まった | `エラー:` の行を見る（ノートブックの出力、または `log.jsonl`） |
| 「速度：--」「準備中：…」が長く続く | 勝敗の確認と eval_scale の推定に時間がかかっている（全ファイルを読むため） | `status.json` の `phase` を見る。`data_check` と `eval_scale` は、データの大きさに比例して時間がかかる |

## 9. 量子化の確認について

- ノートブックの「8. 量子化の確認」は、**学習に使ったファイルの先頭**で行います。学習中の局面なので、本当の確認にはなりません。
- 本当の確認には、学習に使わなかった PSV（検証用）を `--psv` で指定します。

## 10. Colab でしか確かめていないこと

次のことは、この環境では動かせないため、確かめていません。

- GPU の経路（`device = "auto"` で CUDA を使うこと、固定メモリ経由の転送）。
- Drive との読み書きの速さ（持ち主の実測を除く）。
- ランタイムの切断の挙動（セルの実行中かどうかと切断の関係、切断後に裏のプロセスが残るか）。
- `mon.watch()` の表示（IPython の表示、グラフの日本語フォント）。
- ノートブックの各セル（Drive のマウント、rustup、`git clone`）。
